# Scene Village seam defect — integration decision and gates

Date: 2026-09-24. This is a separate bug-fix task, not a modification to the completed Scene2D plan or the earlier Village feature evidence.

## Decision in force

The user selected the first presented repair option: expose per-instance image sampling on `Sprite2D`, preserve the existing default **Linear** behavior for ordinary sprites, and explicitly use **Point** for the Village Tiny Town atlas sprites. Root subsequently approved the source-backed public shape `Sprite2D.Sampling` of the existing `DrawSamplingMode` type with `SamplingProperty`, a Linear default, and render invalidation (`AffectsRender`) when changed. This initial decision did not authorize a GPU backend change, global sampler change, padded-asset replacement, or blanket clamp. The later, narrowly scoped private backend contract is recorded below; it refines this public Point opt-in rather than replacing it.

Observed symptom: straight seam lines are visible along tiled Village background boundaries in the app-owned native screenshots. The focused native reproduction and ownership diagnosis belong to the Village and Core workers. The initial full Village solution result (6,318 passed, 0 failed, six skipped) is a pre-seam historical baseline, not post-fix verification.

The initial Point-only narrow GREEN did not establish visual completion. Raw commands and observations are in `../app/diagnosis.md`. MSAA coverage/UV interpolation is a falsifiable hypothesis, **not** an assigned root cause. Core is running a controlled renderer experiment; no backend production fix has been approved from this evidence alone.

A subsequent controlled shader A/B reported all six Point phases GREEN with centroid UV interpolation and three phases RED after restoring the original shader. The Core owner restored the shader source/artifacts and verified their hashes; this is a discriminating experiment, not final conformance. ## User-confirmed private image-domain contract (2026-09-25)

After the logical-domain diagnostic, the user explicitly selected a **private** image-region edge rule beneath the already approved public `Sprite2D.Sampling` Point opt-in. It applies **only to Point + Clamp** image draws. Evaluate ordinary pixel centers within the declared logical image region; when a covered pixel center lies outside that region, use a covered position inside it. Fractional source rectangles retain nearest-neighbor semantics without a blanket half-texel shrink. The region belongs to each selected image, not to an entire batch or an internal mesh triangle.

The private rule covers `DrawImage`, each sprite in sprite batches, options-based image quads, and nine-slice drawing relative to the **whole selected image region** (not each of its nine patches). Linear, Wrap, arbitrary meshes, surface composites, and other rendering paths remain unchanged. The public API remains the previously approved `Sprite2D.Sampling`/`SamplingProperty`; this decision does not authorize another public API, a global sampler rule, or the rejected generic-centroid shader. This is an approved **contract**, not a claim that a renderer implementation, native GREEN, or full conformance already exists. Core owns a source-grounded private design and regression proposal before any production edit; integration builds remain on hold until the owner releases the serialized lease.

The original 2026-09-25 wording above specified a covered position only when the pixel center was **outside** the external logical image boundary. A later Village native phase-0.500 reproduction was RED under that interpretation. The user explicitly amended the contract: for Point + Clamp, use a covered position when the pixel center is **on or outside an external boundary** of the declared image region. Pixel centers strictly inside the region, including shared internal triangle diagonals and nine-slice patch seams, retain ordinary evaluation. This amendment supersedes only the outside-only threshold; the selected paths and unchanged Linear/Wrap/arbitrary-mesh/composite exclusions remain in force. The prior 925-case SDL run predates this amendment and is not final conformance evidence. Core owns focused RED→fix→native/performance verification under its exclusive lease; no GREEN or full-suite completion is inferred here.

## Approved private implementation boundary (2026-09-25)

Root approved the Core owner's revised design for implementing that contract. Preserve the existing 32-byte vertex layout and ordinary shaders for unrelated drawing. The accepted candidate uses a separate private **64-byte** selected image-domain vertex layout and image-domain vertex/pixel shader pair, with private image provenance and layout-kind routing. Keep the existing single GPU upload arena; use separate ordinary/selected CPU vertex arrays and a reusable packing buffer only when a mixed-layout flush requires it. The selected array is allocated lazily, avoiding the rejected eager 64 KiB selected-array payload for ordinary-only backend construction. Do not split a sprite batch once per crop. This is a bounded renderer-internal design, not a new public API or permission to change ordinary mesh, Linear, Wrap, or composite behavior.

Core owns the specified drawing, SDL backend/Cerberus, upload-layout, shader manifest/artifact, and focused test files under its exclusive build lease. The initial design requested targeted pre-edit cost measurements; the recorded native warm run has no matched pre-change native baseline, so it cannot support a causal throughput/allocation claim. Report only its actual measured current-build workload and structural costs. The shader artifact inventory is expected to grow from eight to ten only if the selected shader pair is implemented and verified; a manifest/build count alone is not shader-byte verification. The post-fix public API comparison must account for the previously approved `Sprite2D.Sampling`/`SamplingProperty` addition and detect any **extra** public/protected surface from this private implementation. No final integration gate is claimed GREEN by this design approval.

The focused boundary oracle keeps ordinary interpolation for a pixel center strictly inside the selected region, including the measured one-ULP interior case; it requires selected covered interpolation for the complementary measured one-ULP exterior case. That oracle is not a blanket crop inset or proof of universal floating-point exactness. Core's native warm run measures the current-build workload, not a matched pre-change native benchmark or GPU time; any cost conclusion must stay within its recorded scenarios and counters. The earlier 933-pass/five-skip SDL-project run predates the final measurement/assertion/storage repairs and is historical, not the final native gate.
