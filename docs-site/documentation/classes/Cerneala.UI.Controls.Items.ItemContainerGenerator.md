# ItemContainerGenerator Class

## Definition
Namespace: `Cerneala.UI.Controls.Items`
Assembly/Project: `Cerneala`
Source: `UI/Controls/Items/ItemContainerGenerator.cs`

Creates, prepares, tracks, recycles, and clears item containers for an `ItemsControl`.

```csharp
public sealed class ItemContainerGenerator
```

Inheritance:
`object` -> `ItemContainerGenerator`

## Examples
Create a generator for an `ItemsControl`, realize its items, and read the metadata stored on the generated containers.

```csharp
using Cerneala.UI.Controls;
using Cerneala.UI.Controls.Items;
using Cerneala.UI.Elements;

ItemsControl itemsControl = new();
itemsControl.SetItems(new[] { "Ink", "Brush" });

ItemContainerGenerator generator = new(itemsControl);
IReadOnlyList<UIElement> containers = generator.Realize();

int firstIndex = ItemContainerGenerator.GetItemIndex(containers[0]);    // 0
object? firstItem = ItemContainerGenerator.GetItem(containers[0]);      // "Ink"
bool firstIsSelected = ItemContainerGenerator.GetIsSelected(containers[0]); // false
```

## Remarks
Every `ItemsControl` creates its own `ItemContainerGenerator` in its constructor and uses it to realize, prepare, recycle, and clear its containers. That instance is not exposed as public API. Code outside the framework can create another generator with the public constructor; the new generator keeps its own `RealizedContainers` and `RecyclePool`, separate from the control's own generator. The generator uses the owning control to inspect items, choose container types, create containers, prepare containers, and clear containers.

`GetItemIndex`, `GetItem`, `GetIsSelected`, `SetInfo`, and `ClearInfo` are static. They read and write metadata attached to a container, so they work for containers produced by any generator, including the control's own one.

`Realize` computes the requested item range from an optional `RealizationWindow`, clamps it to the owner's current view item count, recycles any realized containers outside that range, and returns containers for the requested indexes in order. `GetOrCreate` returns an already realized compatible container when possible, and prepares it again when its recorded item or index differs from the item and index requested, or when its recorded selection flag differs from the owner's `IsItemSelected(index)`. If the existing container is not compatible with the current item and container type, it is recycled before a replacement is obtained. A container whose recorded item is the container itself is compatible only with that item, so it is never prepared for another item, even when the container type matches. A container that shows another item is not compatible with a `UIElement` item whose type is the type that `GetContainerTypeForItem` returns or derives from it, because `CreateItemContainer` can return that item as its own container; the container is recycled and the item is realized as described below. A realized container that still shows the requested item, that is, whose recorded item is that item, is kept whatever its type, even when it is not of the type that `GetContainerTypeForItem` returns: it is the container that `CreateItemContainer` returned for that item, because a change of the owner's `ItemTemplate`, `ItemTemplateKey`, `ItemsPanel`, `DisplayMemberPath`, `ItemContainerAspect`, or `ItemsSource` recycles every realized container first.

The control's own generator follows item changes whose position is known, before the control's selection follows them. When items are removed, the containers of the removed items are recycled. When items are inserted, removed, or moved, every other realized container moves to the current index of its item, so `RealizedContainers` stays keyed by the current item index. A container that moved keeps its recorded index until the next `Realize` or `GetOrCreate` prepares it for the new index. A `Selector` item click does not compare this recorded index with the realized key: it selects the index at which the container is realized now, so a click in this window selects the item the clicked container shows. When an item is replaced, its container keeps the index and is prepared for the new item, or recycled if it is not compatible, by the next realization. Until then the container still shows the replaced item, not the item at its index, so a `Selector` item click on it selects nothing, and a selection change does not prepare it. The next realization prepares it with the current selection even when the original item was put back at that index in the meantime. For example, a `ListBox` holds the items `a` (a `ListBoxItem`) and `"str"`, `a` is realized, and `SelectedIndex` is `0`. After `listBox.Items[0] = "x"` the selection is cleared, and after `listBox.Items[0] = a` and the next realization, `SelectedIndex` is `-1`, `a.IsSelected` is `false`, and `GetIsSelected(a)` returns `false`. A replaced item that was its own container is not compatible with the new item, so the next realization recycles it. The exception is a container that wraps a replaced `UIElement` item, such as the `ListBoxItem` generated for a `UIElement` that is not a `ListBoxItem`: that container is recycled when the replacement is reported, so the element is released at once and can be wrapped by the container at its new index. A reset, or a change whose position is unknown, recycles every realized container. A generator created with the public constructor is not notified of item changes.

For example, a `ListBox` holds three `UIElement` items `e0`, `e1`, and `e2`, each wrapped in a `ListBoxItem`. After `listBox.Items.RemoveAt(0)`, the container that showed `e0` is recycled and its `Content` is `null`. `RealizedContainers[0]` is the container that shows `e1`, and `RealizedContainers[1]` is the container that shows `e2`. A `TabItem` item is its own container, so removing it detaches it and clears its item state, but its `Content` is kept.

For example, a `ListBox` holds the `UIElement` items `e0` and `e1`, each wrapped in a `ListBoxItem`, and the two items are swapped with `listBox.Items[0] = e1` and then `listBox.Items[1] = e0`. Each assignment recycles the `ListBoxItem` that showed the replaced element, so its `Content` becomes `null`. After the next layout, `RealizedContainers[0]` shows `e1` and `RealizedContainers[1]` shows `e0`, and each element is the `Content` of only one container. Swapping the items of an `ObservableCollection<UIElement>` used as `ItemsSource` works the same way.

A container that is its own item, such as a `ListBoxItem` placed directly in a `ListBox`, belongs to that item rather than to an index. If such a realized container is still keyed by an index that no longer holds its item, `Realize` moves it to the current index of its item before it recycles the containers outside the requested range, and then prepares it for that index; the container is not cleared, detached, or recycled. This happens in a generator that is not notified of item changes. For example, `ItemContainerGenerator generator = new(listBox)` realizes the `ListBoxItem`s `a`, `b`, and `c` of `listBox`. After `listBox.Items.RemoveAt(0)`, the next `generator.Realize()` recycles only `a`; `b` is realized at index `0` with `ItemIndex` `0` and `Item` `b`, and `c` at index `1`. The control's own generator already moved `b` and `c` to the keys `0` and `1` when the removal was reported, so its next `Realize` only prepares them for their new indexes. `Realize` keys every moved container by its new index before it prepares any of them. If the owner's `PrepareItemContainer` throws for one of them, the exception propagates, and every moved container, including the one whose preparation threw, stays in `RealizedContainers` at its new index: `Recycle`, `Clear`, or the removal of its item clears it later, and the next `Realize` that succeeds prepares it again when its recorded item, index, or selection flag differs. For example, if the `generator.Realize()` above throws while it prepares `b`, `b` is still realized at index `0` and `c` at index `1`, and after `generator.Clear()` both have `ItemIndex` `-1` and `GetItem` returns `null` for both. When the new index of a moved container still holds another container that does not move, `Realize` recycles that container before it moves any container. If the owner's `ClearItemContainer` throws for it, the exception propagates, the container whose clear threw is not realized any more, and every container that `Realize` would have moved stays in `RealizedContainers` at its previous index: `Recycle`, `Clear`, or the removal of its item clears it later, and the next `Realize` that succeeds moves it. For example, if `ClearItemContainer` throws for `a` during the `generator.Realize()` above, `b` is still realized at index `1` and `c` at index `2`. After `generator.Clear()` both have `ItemIndex` `-1` and `GetItem` returns `null` for both; a `generator.Realize()` after `ClearItemContainer` stops throwing instead realizes `b` at index `0` and `c` at index `1`.

`GetOrCreate(index)` moves such a container the same way when it is called directly: if the item at `index` is a container that is its own item and is still realized under another index that no longer holds that item, the container is removed from the old key, realized at `index`, and prepared for `index`, without being cleared or detached. A container is therefore never realized under two indexes. For example, a `ListBox` holds the items `a` (a `ListBoxItem`) and `"str"`, and `ItemContainerGenerator generator = new(listBox)` realizes `"str"` and `a` while the items are `["str", a]`, so `a` is realized at index `1`. After `listBox.SetItems(new object[] { a, "str" })`, `generator.GetOrCreate(0)` returns `a`, which is now realized only at index `0` with `ItemIndex` `0`, `Item` `a`, and its visual parent unchanged. `generator.GetOrCreate(1)` then realizes the generated `ListBoxItem` that shows `"str"` at index `1`.

Such a container never serves a data item that takes its old index. For example, a `ListBox` holds the items `a` (a `ListBoxItem` with `Content` `"A"`), `"str"`, and `c` (a `ListBoxItem`), and all three are realized. After `listBox.Items[0] = "new"`, the next realization recycles `a` and realizes a generated `ListBoxItem` that shows `"new"` at index `0`. `a` keeps `Content` `"A"`, has no visual parent, has `ItemIndex` `-1`, and is not in `RecyclePool`. The same happens in a generator created with the public constructor after `listBox.Items.RemoveAt(0)`: `a` is still keyed by index `0`, and the next `Realize` recycles it and shows `"str"` in a generated `ListBoxItem`.

Recycled containers are stored in `RecyclePool` by concrete container type. If the item is itself the generated `UIElement`, the generator clears and detaches it but does not push it into the recycle pool. An item that its owner realizes as itself, such as a `ListBoxItem` item in a `ListBox` or a `UIElement` item in an `ItemsControl` without an `ItemTemplate`, never takes a recycled container from the pool. For example, a `ListBox` holds the items `"str"` and `a` (a `ListBoxItem` with `Content` `"A"`). `Realize(new RealizationWindow(0, 1))` realizes a generated `ListBoxItem` that shows `"str"`, and `Realize(new RealizationWindow(1, 2))` then returns `a` itself; `a` keeps `Content` `"A"`, and the generated `ListBoxItem` stays in `RecyclePool` with `Content` `null`. An `ItemsControl` with an `ItemTemplate` wraps every item in a `ContentPresenter`, a `ContentPresenter` item too, so that wrapper is an ordinary container: each later `Realize` returns the same wrapper, and `RecyclePool` stays empty. An item can be its own container only when it is a `UIElement` whose type is the type that `GetContainerTypeForItem` returns or derives from it; `CreateItemContainer` then decides whether it is, by returning the item itself. For example, an `ItemsControl` subclass whose `GetContainerTypeForItem` returns `typeof(ContentPresenter)` and whose `CreateItemContainer` returns `new ContentPresenter()` holds one item, a `ListBoxItem`: a `ListBoxItem` is not a `ContentPresenter`, so the first `Realize` wraps it in a `ContentPresenter`, each later `Realize` returns that same `ContentPresenter`, and `RecyclePool` stays empty. When the item is of that type, the generator asks `CreateItemContainer` before the pool, and uses the item itself when `CreateItemContainer` returns it. For example, a `ListBox` subclass whose `GetContainerTypeForItem` returns `typeof(ListBoxItem)` for every item, and which keeps the `CreateItemContainer` of `ListBox`, holds the items `"str"` and `a` (an instance of a class derived from `ListBoxItem`, with `Content` `"A"`). `Realize(new RealizationWindow(0, 1))` realizes a generated `ListBoxItem` that shows `"str"`, and each later `Realize(new RealizationWindow(1, 2))` returns `a` itself with `ItemIndex` `1`; `a` keeps `Content` `"A"`, and the generated `ListBoxItem` stays in `RecyclePool` with `Content` `null`. If the subclass still returns a new container instead of the item, the generator takes a recycled container of that type when `RecyclePool` has one, so `RecyclePool` does not grow on each `Realize`. This applies to a subclass with an `ItemTemplate` too. For example, an `ItemsControl` subclass whose `GetContainerTypeForItem` returns `typeof(ListBoxItem)` and whose `CreateItemContainer` returns the item when it is a `ListBoxItem` and `new ListBoxItem()` otherwise has an `ItemTemplate` and holds the items `"str"` and `a` (a `ListBoxItem` with `Content` `"A"`). `Realize(new RealizationWindow(0, 1))` realizes a generated `ListBoxItem` that shows `"str"`, and each later `Realize(new RealizationWindow(1, 2))` returns `a` itself; `a` keeps `Content` `"A"`, and the generated `ListBoxItem` stays in `RecyclePool` with `Content` `null`. If the same control instead holds `"str"` and `"b"`, all realized, and then `Items[0] = a`, the next `Realize` recycles the generated `ListBoxItem` that showed `"str"` and returns `a` at index `0`. That wrapper, or any other wrapper that already shows such an item, then stays the item's container while it shows the item, whatever the wrapper's type. For example, if the `ContentPresenter` subclass above holds one item, a `ContentPresenter` with `Content` `"P"`, the first `Realize` wraps it in a new `ContentPresenter`, and each later `Realize` returns that same wrapper without detaching it from its parents, clearing it, calling `CreateItemContainer`, or preparing it again while the item keeps its index and selection. The same holds for an `ItemsControl` subclass that overrides only `CreateItemContainer` to return `new ContentPresenter()` and holds a `Button`: `GetContainerTypeForItem` returns `typeof(Button)`, the first `Realize` wraps the `Button` in a `ContentPresenter`, each later `Realize` and each layout returns that same `ContentPresenter` with `Content` the `Button`, and `RecyclePool` stays empty. A data item is treated the same way: if such a subclass returns `new ListBoxItem()` from `CreateItemContainer` and holds `"s"`, `GetContainerTypeForItem` returns `typeof(ContentPresenter)`, and each `Realize` returns the same `ListBoxItem` with `Content` `"s"`. Once recycled, such a container is stored in `RecyclePool` under its own type, `ListBoxItem`, and `GetOrCreate` takes it back only for an item whose `GetContainerTypeForItem` returns that type, so a subclass whose recycled containers should serve other items returns their type from `GetContainerTypeForItem`.

When the owner's `PrepareItemContainer` throws for a container that `GetOrCreate` took from `RecyclePool` or from `CreateItemContainer`, the container is not realized. The generator calls the owner's `ClearItemContainer` for it, pushes it back into `RecyclePool` unless it is its own item, and the exception propagates to the caller. For example, an `ItemsControl` with an `ItemContainerAspect` holds `"a"` and `"b"`, both realized, and then gets the items `"x"` and `"y"`, so `RecyclePool.Count` is `2`. If `PrepareItemContainer` throws during the next layout, `RealizedContainers` is empty, `RecyclePool.Count` is still `2`, and both pooled containers have `Aspect` `null` and `GetItemIndex` `-1`; a layout that throws again does not change these values, and the next layout that succeeds reuses both containers. A `UIElement` item that is its own container likewise has `Aspect` `null`, `GetItemIndex` `-1`, and `GetItem` `null` after its preparation throws, and it keeps its own content, even when `PrepareItemContainer` throws before the base preparation records the item. For example, an `ItemsControl` subclass without an `ItemTemplate`, whose `PrepareItemContainer` throws before it calls the base method, holds one item, a `ListBoxItem` with `Content` `"A"`: after the failed `Realize`, the item still has `Content` `"A"`. A `MenuItem` item of a `Menu` keeps its `Header` the same way.

When the owner's `PrepareItemContainer` throws while `GetOrCreate` or `Realize` prepares a container that is already realized, for example for a replaced item or for a container that is its own item and moved to a new index, the container stays in `RealizedContainers` and the exception propagates to the caller. The failed preparation can have recorded the new item before it threw, so the generator sets the recorded index to `-1` and keeps the recorded item and selection flag. The next `GetOrCreate` for that index therefore prepares the container again, and throws again while the preparation keeps throwing. For example, an `ItemsControl` subclass whose `PrepareItemContent` throws for `"b"` shows `"a"` in a `ContentPresenter`. After `Items[0] = "b"`, each layout throws, and after that container `GetItemIndex` returns `-1` and `GetItem` returns `"b"`. The first layout after `PrepareItemContent` stops throwing prepares the same `ContentPresenter` again, so its `Content` is `"b"` and `GetItemIndex` returns `0`. Until such a container is prepared again, a `Selector` item click on it selects nothing, even when its recorded item equals the item at its index. For example, a `ListBox` whose `PrepareItemContent` throws for `"x"` shows `"a"`, `"b"`, and `"c"`; after `Items[1] = "x"` and a layout that throws, the row still shows `"b"`, `GetItem` returns `"x"` for it, and a click on it leaves `SelectedIndex` at `-1`.

Container metadata is stored separately from the container instance. `GetItemIndex` returns `-1` when no metadata exists, `GetItem` returns `null` when no item is recorded, and `GetIsSelected` returns `false` when no selection flag is recorded.

## Constructors
| Name | Description |
| --- | --- |
| `ItemContainerGenerator(ItemsControl owner)` | Initializes a generator for `owner` and creates an empty `ItemContainerRecyclePool`. Throws `ArgumentNullException` when `owner` is `null`. |

## Properties
| Name | Type | Description |
| --- | --- | --- |
| `RecyclePool` | `ItemContainerRecyclePool` | Gets the pool used to reuse detached containers by concrete container type. |
| `RealizedContainers` | `IReadOnlyDictionary<int, UIElement>` | Gets the currently realized containers keyed by item index. For the control's own generator, the keys follow inserted, removed, and moved items. |

## Methods
| Name | Return type | Description |
| --- | --- | --- |
| `Realize(RealizationWindow? window = null)` | `IReadOnlyList<UIElement>` | Realizes containers for the requested window, or for all items when `window` is `null`, moves realized containers that are their own items from an old index to their items' current indexes, and recycles containers outside that range. |
| `GetOrCreate(int index)` | `UIElement` | Returns the compatible realized container for `index` (prepared again when its recorded item, index, or selection flag differs from the current one; a container that is its own item is compatible only with that item; a container that shows another item is not compatible with a `UIElement` item of the container type or of a type derived from it, and a container that already shows that item stays compatible whatever its type), moves a realized container that is its own item from an old index that no longer holds that item to `index` and prepares it there without clearing or detaching it, reuses a recycled container when available, or asks the owner to create and prepare a new container. For a `UIElement` item of the container type or of a type derived from it, it asks `CreateItemContainer` first and takes a recycled container only when the returned container is not the item. When the owner's `PrepareItemContainer` throws for a new or recycled container, it clears that container, returns it to `RecyclePool` unless it is its own item, and rethrows. When it throws for the realized container, that container stays realized with recorded index `-1`, so the next call prepares it again, and the exception is rethrown. Throws `ArgumentOutOfRangeException` when `index` is outside the current item range. |
| `Recycle(int index)` | `void` | Removes the realized container for `index`, detaches it from visual and logical parents, clears owner-specific container state, and stores it in `RecyclePool` when it is reusable. |
| `Clear()` | `void` | Recycles every currently realized container. |
| `GetItemIndex(UIElement container)` | `int` | Returns the item index recorded for `container`, or `-1` when no index is recorded. After an item change, a moved container's recorded index can differ from its `RealizedContainers` key until the container is prepared again. A realized container whose preparation threw has recorded index `-1` until it is prepared again. Throws `ArgumentNullException` when `container` is `null`. |
| `GetItem(UIElement container)` | `object?` | Returns the item recorded for `container`, or `null` when no item is recorded. Throws `ArgumentNullException` when `container` is `null`. |
| `GetIsSelected(UIElement container)` | `bool` | Returns the selection flag recorded for `container`; returns `false` when no flag is recorded. Throws `ArgumentNullException` when `container` is `null`. |
| `SetInfo(UIElement container, int index, object? item, bool isSelected)` | `void` | Records item index, item value, and selection state for `container`. Throws `ArgumentNullException` when `container` is `null`. |
| `ClearInfo(UIElement container)` | `void` | Resets the recorded metadata for `container` to index `-1`, item `null`, and unselected state. Throws `ArgumentNullException` when `container` is `null`. |

## Applies to
`Cerneala.UI.Controls` item controls that realize, recycle, and describe item containers.
